## t-019 — relay_media_agent.py rejects the legitimate public/rewards/... path, permanently failing daily-dream reward-art jobs

<!-- note:begin t-019 -->
Filed 2026-07-25 (ai-art-academy/t-010 lane 2, roadmap-accuracy cycle, while spot-checking the shared art-queue relay's live health). A fresh `GET /api/art/queue/stats` (authenticated) showed the relay is not fully down (RUNNING: 1, DONE: 1438 in the last 24h) but its `recentFailed` list includes three exhausted-retry jobs from 2026-07-24 21:37-21:47 UTC, all the same error: "Kind Robots media job imagePath must begin with public/images/" (job ids 2219/2220/2221 — Friendly Bartender, Dr. Eliza Dolittle's Ring, Bag of Mushrooms reward-item art). Pulled each job's full payload directly: `imagePath: "public/rewards/favor/*.webp"`, `targetRepo: "silasfelinus/kind_robots"`. That path is CORRECT, not malformed — confirmed `public/rewards/` (favor/item/pet/power/skill) is a real, separate top-level directory in the kind_robots repo, sibling to `public/images/`, not nested under it (there is no `public/images/rewards/`). `projects/art-prompts.yaml` has 18 existing entries using this exact `public/rewards/<type>/<slug>.webp` convention (e.g. line ~532 `kind-robots-friendly-bartender-image-2e3cf8c7`), matching the header note in `scripts/dream_slug_image_cleanup.py` ("Reward image folders (/rewards/<type>/... vs the component's /images/rewards/...)") — this is the project's own established, intentional path convention for reward art, not a caller bug.
Root cause is in `ops/home-server/relay_media_agent.py`'s `direct_media_relative()` (~line 82): it hard-requires `parts[:2] == ("public", "images")` and raises `ValueError` otherwise, so any `public/rewards/...` job reaches the relay, fails validation, retries 3x, and lands in FAILED — the daily-dream reward-art pipeline (t-018's output) silently loses its art with no successful fallback path, distinct from the already-documented "relay never claims the job" backlog signature lane 3 has tracked since 2026-07-18 (this is a claimed-then-hard-rejected job, not an unclaimed one).
NOT fixed inline this cycle (out of lane 2's docs-only scope, and the fix is not as simple as widening the validator's accepted prefix): `media_root()` resolves everything under the single `KR_MEDIA_IMAGES_DIR`/`KR_LOCAL_IMAGES_DIR` env var, which points at the physical folder backing `public/images/` on Silas's home-server box. Naively accepting `public/rewards/...` and stripping it the same way `write_direct_media()` does for `images/...` would write the file under `<KR_MEDIA_IMAGES_DIR>/rewards/...` — i.e. inside `public/images/rewards/...` on the box, NOT the real sibling `public/rewards/...` the job actually requested — silently landing the generated art in the wrong folder while the job reports success. A correct fix needs either a second root env var (e.g. `KR_MEDIA_REWARDS_DIR`) or a single "public root" env var with `images`/`rewards` as two recognized subpaths under it, wired through `media_root()`/`write_direct_media()`, and updated/added test coverage alongside the existing `tests/test_media_direct.py` cases (`test_relay_maps_legacy_kindrobots_paths`, `test_relay_rejects_unsafe_kindrobots_paths` — note the latter explicitly expects unrecognized public/* roots like `public/assets/...` to keep raising, so this needs to whitelist `rewards` specifically, not loosen the check generally). Needs Silas's read on his box's actual folder layout before landing, since a wrong guess fails silently (job succeeds, file lands in the wrong place) rather than loudly.
FIXED 2026-07-29 (conductor burst-mode cycle, claude-conductor-burst-20260729T121718Z-dc-t019): landed the second-root fix this note called for, and found the situation had actually gotten worse since filing — a since-merged, unrelated PR (#1399, 2026-07-28) had added `ops/home-server/relay_media_agent.py`'s `normalize_kindrobots_image_path()` with a `public/rewards/...` → `public/images/rewards/...` rewrite, plus a matching `tests/test_media_rewards.py` that locked that behavior in as correct (test named `test_relay_uses_configured_image_root_without_sibling_mapping`). Implemented the actual fix: added `KR_MEDIA_REWARDS_DIR`/`KR_LOCAL_REWARDS_DIR` as a second, independent root (mirroring the existing images env-var pattern); `normalize_kindrobots_image_path()` now canonicalizes `rewards/...`/`public/rewards/...` to `public/rewards/...` (not folded into images); `direct_media_target()` accepts either `public/images/...` or `public/rewards/...` and returns the matching kind; `media_root(kind)` is parametrized and raises a clear `RuntimeError` naming the missing env var per kind instead of guessing a path. Kaizen from PR #3390 (conductor sweep, 2026-09-01): daily-dream-prose-repair.yml was discarding an entire batch (13+ good repairs) whenever a single bundle came back as an empty Claude completion, which #3390 fixed by making atomicity per-bundle instead of per-batch -- a failed bundle is now left untouched, recorded in `failed_bundles`, and simply retried next run. That's the right fix for a transient flake, but nothing yet distinguishes "flaky, will succeed eventually" from "this specific bundle's content reliably triggers an empty completion" (e.g. a content-policy edge case in its own proposal text) -- such a bundle would now retry silently forever, once per scheduled run, with nobody ever told. Track consecutive failure counts per bundle (day/title) across runs -- e.g. a small state file alongside the backlog, or a count embedded in the audit -- and once a bundle hits some small threshold (3-5 consecutive failed runs), stop auto-retrying and surface it explicitly (a needs-human note, or at minimum a distinct stderr/receipt marker a human sweep would notice) rather than let it recur unnoticed indefinitely.
Closed: chronic-failure circuit breaker merged as conductor#3507 (implementation), conductor#3508 (review bookkeeping). All CI green except the two documented recurring non-required stragglers.

## t-026 — Character Facets were never applied - digest reported complete over an empty record

<!-- note:begin t-026 -->
FILED WRONG, THEN CORRECTED. This task first read "facets per dream have drifted past the 1-2 the seed spec asks for", from Silas asking "are we really making four facets per dream? That was not on spec". I could not measure the count from the public API and said so, but I framed the whole thing as a count question. It was not. Silas supplied the missing evidence himself: "I just don't get the facets added as part of my daily digest, so there is a discrepancy ... While I don't have an issue with four facets in one day, ten generations for dream is ok ... mostly I want parity between what is being made and what is being reported in my daily dream updates and my front end dashboard." His digest showed the real numbers -- the vibe carries 4 seed facets and the whole bundle spans about 11 distinct ones -- and he is fine with that. The count was never the problem. The reporting was. THE ACTUAL BUG. PUT /api/characters/:id/facets read `assignments` or `facetIds` and nothing else. This script sends `{facetIds: [], facetKeys: [...]}` because slugs are the durable address (ids go stale when catalog rows merge or are deleted), so the body normalized to zero assignments -- and the handler's unconditional deleteMany still ran. It cleared the Character's Facets, created nothing, and answered success with an empty catalog. Every one of the 36 built bundles recorded status "complete" with errors [] over a Character carrying no Facets. Confirmed on production: GET /api/characters/3320/facets returns data: [] for a bundle that requested six, while the same bundle's Dream (4), Rewards and Scenario all carry theirs. THE TESTS WERE PROTECTING IT. tests/test_apply_daily_dream_facets.py stubbed _put to return `{"success": true, "data": []}` -- the exact response the broken endpoint gave -- and asserted status == "complete" against it. The suite encoded the bug. Fixed, plus a case that a target attaching nothing is now partial with an error, and one that --dry-run still trusts the request it never sent. FIXED IN THREE PLACES, because one would have left a half-truth: (1) kind_robots#2314 makes the Character route resolve facetKeys, mirroring the Reward route that already did, and does the same for Bots, which carried the identical latent defect. verifyFacetSelectionRoutes.ts guards all six Facet-bearing models and fails on the pre-fix route (verified by reverting it). (2) apply_daily_dream_facets.py no longer treats a 200 as proof. A target whose response attaches nothing is an error and the bundle is partial, so "complete" means complete. (3) build_digest_email_v2.py prints what actually landed -- "23 Facet link(s) across 6 record(s); nothing attached to character", amber rather than green, with a per-record breakdown -- instead of the bare word "complete". The data was always in `targets`; it was simply never shown. That is the parity Silas asked for: on the kelp-ink-transfer bundle the new line names the empty Character on sight. The count question is settled and needs no work: 4 seed facets on the vibe, ~11 across the bundle, and Silas has said explicitly that is fine. REPAIRED 2026-09-02, on Silas's word: "Characters (and anything else us8ng facets) should be repaired if missing." A read-only live sweep first, so "anything else" was measured rather than assumed -- of 216 recorded targets, Characters were 36/36 empty and every other element was 0/36. Then apply_daily_dream_facets.py --force, then an independent re-audit: 216/216 targets present, 1045 live Facet links, zero empty, zero short of what was requested. scripts/check_live_facet_coverage.py keeps it that way and is in the session sweep; its tests cover the failing shapes, not just the passing one, because the guard this replaces had only ever passed.
