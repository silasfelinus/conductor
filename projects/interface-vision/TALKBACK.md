**Subject:** Closed t-003b via kind_robots PR #1261, merged after one review-caught composition bug fixed in the same PR.

**Detail:**
- Flipped `app.vue`'s `NuxtPage` wrapper to `overflow-hidden` and made `pages/[...slug].vue`'s `content-host` the scroll owner for every MDC-routed page — the single highest-leverage fix, since about/giving/privacy/sponsor/mermaids/register etc. all render through it. Backfilled ~15 standalone routes/components that render outside `content-host` (WonderLab admin pages, play/challenges pages, coloring-page, music-mentor, build-bench, appmaker-page, click/match-leaderboard, super-form). Found and fixed two latent bugs along the way: `login-page.vue` and `welcome-page.vue` each already declared `overflow-y-auto` but on an unbounded `min-h-full`/`min-h-screen` container, so it never actually engaged.
- First push also added per-component scroll classes to `about-page.vue`, `giving-page.vue`, `mermaids-page.vue`, `privacy-page.vue`, `sponsor-page.vue`, and `components/user/registration-page.vue` — each of these is mounted *inside* `content-host` via MDC, so this created nested double-scroll regions, the exact composition bug the task existed to remove. A `kr-hourly` review session caught this (confirmed correct via `content/*.md` grep — the review was right on 6 of 7 flagged files; the 7th, `registration-form.vue`, turned out to be unreferenced/orphaned so the concern didn't actually apply there, though I reverted it anyway for consistency). Fixed in a follow-up commit on the same PR; re-verified `test:layout-contract` and `vue-tsc --noEmit` clean before the reviewer merged.
- Root cause of the mistake: I identified files lacking their own scroll region correctly, but for files rendered inside an ancestor that now owns scroll, adding a scroll region anyway is a compositional error the file-by-file layout-contract verifier can't see. Filed t-021 (kaizen, this project) for a composition-aware check per the reviewer's own suggestion.
- Deliberately left several `components/pages/*.vue` and `components/conductor/*-page.vue` files unfixed with reasoning recorded in the PR body: 11 conductor pages + `coloring-book-page.vue` already inherit scroll from the shared `ProjectFrontPage` wrapper; `conductor-manager.vue` and `conductor-art-gallery.vue` correctly delegate to children/parent; `kaizen-popup.vue` is a Teleport modal; `kind-prompts.vue`, `rebel-button.vue`, `social-page.vue` appear orphaned (no route/content mount found for any of them).

**Suggested action:** When a shared ancestor (a layout shell, a content-host, a wrapper component) already owns scroll, verify a candidate file's actual *rendering context* — not just whether the file itself lacks a scroll region — before adding one. A quick `grep -rn ":<component-name>" content/` (or equivalent import-site search) against each candidate before editing would have caught this on the first pass instead of needing a second review round.
