# Mapped Customer Route Planner — Spec

Generated by: humboldt-scoop-cms/t-006
Date: 2026-07-15

This document defines a dispatcher/crew route planner: pick a date/filter and a
start (optional end) location, select up to N eligible customers (or choose
them explicitly), and produce an ordered, mapped, editable route. It is a
draft specification only — no real customer data, live dispatching, billing,
map-provider billing, publishing, or deployment is included or authorized by
this document.

**Soft needs-human note within a hard gate:** this task carries `gate_human: true`
per `notes_from_silas` — "Silas approves provider/shape first." This spec is the
proposal that approval acts on; no implementation should start against a specific
provider/library choice until Silas sets `approved_by_human: true`. Everything
below is a recommendation, not a locked contract.

## 1. Selection model

- **Filter step**: dispatcher picks a service date (or date range) and an
  optional filter (neighborhood, service frequency, service type) to narrow
  the eligible customer/user queue — reusing the same customer/visit records
  `route-cards/SPEC.md` already assumes (dummy data only).
- **Start / end location**: required start point (e.g. "shop" or crew home
  base), optional distinct end point. Defaults to a round trip (end = start)
  if not set.
- **Stop count / selection**:
  - **Explicit mode** — dispatcher checks specific customers off the eligible
    list directly.
  - **Fill-to-N mode** — dispatcher picks a target count N; the planner
    proposes the top N eligible customers (e.g. earliest-due, or by
    proximity to the start point) and the dispatcher can swap any proposed
    stop for another eligible one before routing.
  - Both modes converge on the same intermediate shape: an ordered array of
    `stopCandidate` records (customerId, address/coords, service window if
    any) that gets handed to the routing step.

## 2. Ordered stop list, map, and estimates

Once candidates are chosen, the planner:

1. Calls a routing/optimization backend (§3) with the start, end, and
   candidate stops to produce a **visit order** (not just a distance matrix —
   the optimizer decides order, subject to manual overrides in §4).
2. Renders the ordered route as:
   - A **polyline on a map** (turn-by-turn geometry from the router, not a
     straight-line stop-to-stop guess).
   - A **per-stop route card list**, extending `route-cards/SPEC.md`'s
     existing card fields with routing-specific ones: stop sequence number,
     leg distance/time from the previous stop, running ETA, and a
     locked/skipped flag (§4).
3. Shows **aggregate estimates**: total distance, total drive time, and
   estimated finish time (crew start time + cumulative drive + a
   per-stop service-duration constant from the customer's service type —
   no live traffic dependency required for v1).

## 3. Routing/optimization engine comparison

Two separable concerns: (a) **road-network routing** — the distance/time
matrix and turn-by-turn polyline between real stops, and (b) **stop-order
optimization** — deciding the best visit sequence given that matrix
(a Traveling-Salesman-with-time-windows-style problem, not something an LLM
should attempt per `notes_from_silas`'s explicit "do NOT use an LLM for
routing" rule).

### 3a. Self-hostable stack

| Component | Role | Notes |
| --- | --- | --- |
| **OSRM** (Open Source Routing Machine) | Road-network matrix + turn-by-turn polyline | C++ engine, MIT-licensed, runs as a local HTTP service over an OpenStreetMap extract (Humboldt County-sized extract is tiny — single-digit MB). Mature, fast, widely used as the default backend for Leaflet Routing Machine. Weak on live traffic (not needed for this use case) and on native multi-stop optimization (handles matrix/route generation, not order-picking). |
| **VROOM** (Vehicle Routing Open-source Optimization Machine) | Stop-order optimization | Open-source (BSD), pairs directly with OSRM's matrix output (or GraphHopper/Valhalla) to solve the visit-order problem — this is the actual "N stops, best order" solver, not just routing. Solves in milliseconds at this scale (dozens of stops, not thousands). |
| **GraphHopper** or **Valhalla** | Alternative to OSRM | Similar self-hosted road-network engines; OSRM is the more common Leaflet-ecosystem default and is the simpler of the two to stand up for a single-region extract, so it's the v1 pick over these. |
| **Leaflet + Leaflet Routing Machine** | Map + polyline rendering, draggable waypoints | Leaflet is a small, mature, self-hostable map client (works with self-hosted OSM tiles or a free tile provider); Leaflet Routing Machine already supports pointing at a custom `serviceUrl` (i.e., a self-hosted OSRM instance) and supports draggable waypoints out of the box, which covers most of §4's manual-reorder requirement on the map itself. |

**Self-hosted cost/effort**: a small VM (or a container alongside the CMS's
Hono service) running `osrm-backend` against a Humboldt-County-scale OSM
extract, plus `vroom` as a second small binary/service reading OSRM's table
output. No per-request billing, no API keys, no third-party data sharing of
customer addresses. Tradeoff: Silas/the crew owns uptime and OSM data
refreshes (quarterly extract re-download is plenty for a service area this
size — roads don't change that often).

### 3b. Paid-API stack

| Provider | Role | Notes |
| --- | --- | --- |
| **OpenRouteService (hosted)** | Matrix + routing + optimization | Free tier exists (small daily quota); paid Starter tier is ~20 EUR/month for 500,000 requests/month — likely more than this business ever needs, so the free tier alone may suffice, but it's still third-party request billing/dependency risk if it changes terms. |
| **Mapbox Optimization API / Directions API** | Matrix + routing + optimization + polished map tiles | Well-documented, has a real optimization endpoint (not just routing), but is metered per request and requires an API key with billing attached — a live-dependency and cost-tracking burden for a business this size. |
| **Google Maps Routes API / Route Optimization API** | Same shape as Mapbox | Same tradeoffs: powerful, but metered, keyed, and puts customer address data through a third party. |

**Paid-API cost/effort**: near-zero infra to run, but a live billing
relationship, an API key that must live server-side (never client-side, per
`notes_from_silas`'s "keys server-side" rule for approved AI features — the
same principle applies here), and every route calculation sends real
customer addresses to an external company. That last point cuts against the
CMS's own stated privacy posture (dummy data now, real customer data later
under explicit approval) — a paid API is a second business the data has to
be trusted to, on top of Silas's own server.

## 4. Interaction requirements (client-side, backend-agnostic)

These apply regardless of which routing backend from §3 is chosen —
they're client/UI behaviors layered over whatever ordered-stop-list-with-geometry
response the backend returns:

- **Manual drag reorder**: the per-stop route-card list (and/or the map's
  waypoint markers, via Leaflet Routing Machine's built-in drag support)
  lets the dispatcher override the optimizer's proposed order. Reordering
  triggers a route-geometry recompute (new polyline + updated per-leg
  distance/time) but does not re-run the stop-selection step.
- **Locked stops**: a stop can be pinned to a fixed position in the sequence
  (e.g. "must be first — client working from home this morning"); the
  optimizer treats locked stops as fixed points and only re-orders the
  unlocked remainder around them. (VROOM supports this via its job/priority
  and time-window constraints; a v1 without full VROOM integration can
  implement it more simply as "optimize the unlocked subset, splice locked
  stops back in at their fixed index.")
- **Skipped customers**: any eligible customer not selected (explicit mode)
  or dropped from the proposed N (fill-to-N mode) is shown in a visible
  "skipped this run" list — not silently omitted — so the dispatcher can
  requeue them for the next route without re-deriving who got left out.
- **Save/export**: persist the finalized route (ordered stop list + locked
  flags + computed geometry/estimates) as a draft record tied to the service
  date, and support exporting it to the same PDF/route-card path
  `route-cards/SPEC.md` already specifies — the route planner's output
  should feed that spec's card renderer rather than inventing a second
  export format.

## 5. Recommended v1 path and fallback

**Recommended v1: self-hosted OSRM + VROOM + Leaflet stack (§3a).**

Reasons this wins for Humboldt Scoop's shape specifically:
- Zero per-request billing and no API-key/secrets surface to manage for the
  core routing feature — consistent with the project's "self-hostable,
  simple" direction in `CONTROL.md`.
- Keeps (eventually real) customer addresses inside Silas's own
  infrastructure rather than sending them to a third party on every route
  calculation — the strongest privacy posture available for the group of
  options considered.
- A single-county OSM extract is small; OSRM's memory/CPU footprint at this
  scale is modest enough to run alongside the existing Hono service or as a
  small sibling container, not a dedicated ops burden.
- VROOM directly solves the "N stops, best order, with locked stops" problem
  this task actually asks for, rather than only giving a distance matrix
  the app would have to optimize itself.

**Fallback: OpenRouteService's free/hosted tier**, if standing up and
maintaining the OSRM+VROOM services turns out to be more infra work than
Silas wants to own for a first version. It covers the same matrix +
optimization + routing shape via one hosted API, at no cost for this
business's low route volume, with the tradeoff of sending stop coordinates
to a third party and a live external dependency. This is a same-vendor
swap-in-place fallback, not a redesign — the client-side interaction model
in §4 and the export path in §4 don't change based on which backend answers
the routing/optimization calls.

**Explicitly not recommended for v1**: Mapbox/Google paid optimization APIs.
They're the most polished option but add real per-request billing and a
third-party address-sharing relationship this business's scale doesn't need
yet; revisit only if OSRM/VROOM/ORS all prove insufficient at a much larger
future stop volume.

## 6. Field-client note (Android first)

`notes_from_silas` names Android as the first field-client target, with
Linux and iOS as compatibility goals. This spec's backend choice (§5) is
client-agnostic — OSRM/VROOM/ORS all speak plain HTTP/JSON, so an Android
client (native, or a cross-platform shell consistent with `conductor-app`'s
existing Flutter direction, if that's reused here) consumes the same route
JSON a web dispatcher view would. Leaflet itself also has usable mobile
WebView behavior if a hybrid app shell is preferred over a fully native map
view — a decision this spec defers to whichever client architecture Silas
picks for the Android app itself (out of scope here).

## 7. Privacy and guardrails

- Dummy addresses only until Silas explicitly approves real customer data
  entry (matches `route-cards/SPEC.md` and `STACK.md`'s existing guardrails).
- No LLM involvement in route computation or stop ordering — routing and
  optimization are deterministic algorithmic steps (OSRM/VROOM or an
  equivalent paid API), never an LLM call, per explicit direction.
- No live map-tile billing, geocoding API billing, or routing API billing
  goes live without Silas's explicit approval of that concrete spend —
  the self-hosted v1 path avoids this entirely; the ORS fallback's free
  tier still needs an account/key decision flagged to Silas before use.
- Real customer addresses, once approved, should only ever reach the
  self-hosted OSRM/VROOM services (§5's recommended path) unless Silas
  explicitly accepts the third-party data-sharing tradeoff of the ORS/paid
  fallback for a specific reason.
