## 2026-08-20 | Agent (scheduled conductor sweep) | kapowarr/t-035 | critique

**Decision:** merged — silasfelinus/Kapowarr#83, all 7 CI checks green, squash `41019cb`.

**Subject:** Building a protocol adapter for a service you cannot reach is exactly
where a plausible-but-wrong implementation gets written, and the thing that made this
one safe was refusing to work from memory.

**What was good:**
- The API reference was assembled from NZBGet's published docs **cross-checked against
  its own C++ implementation** (`XmlRpc.cpp`, `DownloadInfo.cpp`,
  `HistoryCoordinator.cpp`) before a line of client code was written. That was not
  ceremony — the docs are wrong in ways that would have produced a broken client:
  `APPEND.md`'s prose argument list omits the `Content` parameter entirely, and its
  official Python example passes 10 of the 11 arguments in the signature it
  illustrates. Working from either would have mis-ordered `append`.
- Three findings from that pass changed the design rather than just the comments:
  NZBGet speaks **JSON-RPC 1.1** and its replies carry no `jsonrpc` member (a client
  validating one would reject every response); post-processing happens **in the queue**,
  making history terminal — the inverse of SABnzbd, and the reason an unknown history
  status here has to fail rather than wait; and there is genuinely **no per-group
  download rate**, confirmed as a negative rather than assumed as a gap.
- Where a mapping was uncertain, the code keys on the stable part: history statuses
  match on their `PREFIX/` rather than an enumerated suffix list, and unknown
  `listgroups` statuses default to DOWNLOADING. Both are correct for values that don't
  exist yet, which matters for an adapter nobody here can re-test per NZBGet release.
- `delete_download` was worth the reading it got. NZBGet's own conditional disk
  handling already produces exactly what each caller wants — clean disk on a
  cancelled/failed job, leave `DestDir` alone on a successful one — so the mapping is
  a genuine fit rather than a flag translated into the nearest available command.

**What to improve:**
- **Still no live verification, and now that gap is duplicated.** Both Usenet clients
  in this repo carry a "field names not verified against a live instance" caveat in
  their module docstrings. Fixture tests prove the parsing and the state machine; they
  cannot prove the wire contract. This is honest and stated, but it is now a
  two-instance pattern rather than a one-off, and only Silas can close it.
- The `editqueue` four-parameter form was chosen for pre-v18 compatibility without
  knowing whether Kapowarr targets pre-v18 at all. Harmless (newer builds accept it)
  but it is compatibility paid for on spec.

**Pattern note:** second task closed out of kapowarr this session. Both t-034 and t-035
were only reachable because conductor/t-120 fixed the `status: not-started` tasks that
had made this project invisible to the selection queue — see the t-034 entry above and
