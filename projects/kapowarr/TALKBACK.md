## 2026-08-20 | Agent (scheduled conductor sweep) | kapowarr/t-045 | close-out

**Decision:** implemented and merged (Kapowarr#86), task closed `done`.

**Subject:** TAR/CBT support in the built-in reader — plus what the task note got wrong,
and the one place copying the existing pattern would have been a security bug.

**The task was half its stated size.** t-045 reads "Add CBR/RAR and remaining archive
formats to the built-in reader," and its note says to "add safe extraction for CBR/RAR
first, then other practical formats." CBR/RAR was already shipped — `list_rar_pages` and
`read_rar_member` have been in `comic_reader.py` against the bundled RAR executable since
the reader landed. So the entire remaining task was the second clause. The note was
accurate when filed and went stale without anything noticing; a grep before planning is
what caught it. Worth generalizing: a roadmap note describes intent at filing time, not
current state, and nothing in this system ever reconciles the two.

**Scope landed:** TAR/CBT only. `tarfile` is stdlib and `tarfile.open(..., 'r:*')` sniffs
compression, so plain/gzip/bzip2/xz tars all open through one call. `.cb7`/`.7z` is
deliberately still unsupported and now says so in the module docstring — the repo bundles
a RAR binary and gets zip and tar free, but opening 7z needs either a new bundled binary
or a new `requirements.txt` entry, which is a packaging decision and not one to make
silently inside a reader task. Reporting it unsupported beats listing pages that then 404.

**The part that was not mechanical.** The tar functions mirror the ZIP and RAR pairs
nearly line for line, and mirroring them *exactly* would have shipped an
arbitrary-file-read primitive. A tar can carry symlinks, hardlinks, device nodes and
FIFOs; `extractfile()` on a symlink resolves the link target. An archive with a member
named `001.jpg` whose link target is `/etc/passwd` would have had its bytes served
straight back through the authenticated page endpoint. Nothing in the zip pattern being
copied hints at this, because zip cannot express it. The fix is one `isfile()` check,
applied at listing time *and* re-applied in `read_tar_member` — the member name arrives
from a page descriptor built earlier, and the file on disk may have been replaced in
between. Both paths are covered by a test that builds a real symlink member.

**One stale comment corrected, no behavior changed.** `archive_integrity.py`'s docstring
claimed no reader in this codebase could read `.cbt`/`.tar.gz`, which this PR made false.
It still returns `UNSUPPORTED` for tar, now for the accurate reason: a tar has no
per-member checksum, so "opens cleanly" is weaker evidence than the CRC pass its `CORRUPT`
verdict is built on. Whether that weaker signal is worth acting on is a real question and
became the kaizen task (**t-057**) rather than being decided inside this PR.

**Verification:** 581 backend tests OK (13 new), 41 frontend node tests OK, Python 3.8
through 3.12 green in CI, all 7 checks green before merge. `mypy` reports one error, which
is pre-existing on `main` and unrelated (`import_lists.py:240`); confirmed identical with
the diff stashed rather than assumed.

## 2026-08-20 | Agent (scheduled conductor sweep) | kapowarr/t-042 | close-out

**Decision:** evaluation delivered (`docs/t-042-debrid-boundary.md`), task closed
`done`, implementation filed separately as `t-058` at soft `needs-human`.

**Subject:** The task asked whether debrid support fits "without contaminating
generic search/download architecture with a provider-specific shortcut." Answering
that honestly required correcting the question twice.

**Correction 1 — the feature is not the one its name implies.** "Debrid support"
almost universally means the `*arr` torrent-caching pattern: hand a magnet to the
service, wait for its cache, download the result over HTTPS. Evaluating *that*
would have produced a well-argued and completely useless answer, because it has no
home in this codebase — `DownloadState` has no member for the caching wait,
`BaseDirectDownload` resolves its link eagerly in the constructor and would fail
outright on an uncached magnet, multi-file results have no representation, and a
new `DownloadType` member is a breaking settings migration via
`SOURCE_PREFERENCE_OPTIONS`' length-and-set validation.

Upstream #276 is one sentence, and its operative clause is *"instead of having to
use Mega directly."* That is the hoster-unrestrictor pattern, and it maps onto
`BaseDirectDownload._convert_to_pure_link()` so exactly that `PixelDrainDownload`
— which already overrides that hook plus `_fetch_pure_link()` to inject a stored
account credential — is a near-identical template. Same two words, opposite
verdicts, and the only thing separating them was reading the issue instead of the
label.

**Correction 2 — the constraint assumes something untrue.** "Don't contaminate the
generic architecture with a provider-specific shortcut" cannot be evaluated without
first checking whether the architecture is generic. It is not. `__purify_link` is a
flat per-hoster `if/elif` chain; `download_queue.py` special-cases Mega by
`isinstance` to evict the queue; `BaseDirectDownload.__init__` sniffs for
Pixeldrain's rate-limit URL; `TorrentDownload.__init__` calls a third-party web
service; torznab links carry a Kapowarr-invented fragment tag purely so the prepper
registry can route them. Ten such precedents are listed in the document.

The right response was neither to enforce the constraint literally (which would
reject a cheap, well-fitting feature) nor to ignore it, but to report that the seam
is already provider-shaped and that debrid could actually leave it *better* — the
one awkward part, prepper dispatch precedence, is best solved by adding a priority
field the registry wants regardless.

**One correction to my own first draft, worth recording.** The initial pass put the
debrid API token in the `external_download_clients` table alongside SABnzbd and
qBittorrent. That is wrong: `base_url` is mandatory and non-null-checked there (a
debrid provider has none), and the frontend form vocabulary is closed to five fixed
field names. The right home is the separate `credentials` table / `CredentialSource`
enum, which already models "an account credential a direct download consumes to
unlock a link" and which `PixelDrainDownload` already uses that way. Caught by
mapping the two credential systems properly rather than assuming the obvious-looking
one was correct.

**Recommendation recorded as: approve architecturally, don't schedule next.** Not
because of fit, but because debrid is absent from `ARR_PARITY.md`'s near-term list,
and the one risk that actually matters — no reachable account to verify against —
shrinks by waiting for Silas rather than by building sooner. t-035 (NZBGet) shipped
from that same position and its LEARNING entry records that NZBGet's published docs
were wrong about a required parameter, caught only by reading that service's source.
Real-Debrid has no public source to read. Writing untestable code against a paid API
for a userbase of zero is the outcome worth avoiding, and one question from Silas
resolves it either way.
