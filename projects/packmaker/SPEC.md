## 1. What a "pack" is

A pack is a **manifest** — a named, versioned list of content items to be
generated (or already generated) through kind_robots' existing creation
pipelines, bundled as one unit for browsing, gifting, or sale. A pack does
not introduce a new content type of its own; every item in it is an
ordinary kind_robots record, and the pack's only new concept is the
grouping + release lifecycle around those records.

Item types map onto models that already exist today:

| Pack item type | kind_robots model | Notes |
|---|---|---|
| Location | `Dream` (`dreamType: LOCATION`) | Dreams already carry `title`, `description`, `flavorText`, `imagePath`/`cardPath`/`heroPath`, and an optional `Narrator` (`Bot`) — everything a pack location needs. |
| Genre | `Facet` (`kind: GENRE`) | Facets are lightweight reusable tags (genre, mood, style, setting, etc.), linked to Dreams via `DreamFacet`. A pack's genre entries are Facets, not Dreams. |
| Character | `Dream` (`dreamType: CHARACTER`) for narrative/pitch-style cast entries, **or** the standalone `Character` model when the pack wants real stat-block fields (`class`, `species`, `charm`/`empathy`/`grace`/`luck`/`might`/`wits` Rarity ratings, etc.). Uncanny Valor/Arcane Whimsy should default to `Character` rows since the launch packs are meant to power builder items, not just lore — see open question in §7. |
| Reward | `Reward` (`rewardType`, `rarity`, `effect`, `flavorText`) | Reward already has a `Dreams Dream[] @relation("DreamToReward")` many-to-many, so a pack's Dream entries (e.g. a location) can point at the pack's own Reward rows the same way any Dream does today. No new relation needed. |

A pack manifest (t-002's job) is therefore a list of `{ type, refId | draftPayload }` entries plus pack-level metadata (id, title, description, owner, visibility, price hook) — not a new item schema. Draft-stage entries (before generation) carry the same fields the target model needs (title/description/artPrompt/etc.) as a plain payload; once generated, the entry gets a real `refId` into `Dream`/`Facet`/`Character`/`Reward`.

**Pack container itself has no dedicated model yet.** `ArtCollection` (the closest existing grouping construct) is scoped to *art images and prompts* — `imagePath`, `artPrompt`, `parentFolder` — with a one-primary-collection-per-Dream/Facet relationship and no notion of bundling heterogeneous item types or a release/version lifecycle. Reusing it for the pack container itself would be a stretch; a pack can still *use* an ArtCollection as its cover/gallery grouping (see §3), but the manifest (id/title/items/visibility/price) lives in `projects/packmaker/packs/*.yaml` for now, per t-002. Whether that manifest eventually needs its own `Pack` Prisma model (once packs move past "Silas's own drafts" into a real admin CRUD surface) is a question for the generator front end task (t-004/m3), not this brief — see §7.

## 2. Generation reuses existing pipelines — read-only per BOUNDARY.md

Packmaker does not add new generation routes, model routing, or provider
config. Every pack item is produced by calling the same endpoints any other
kind_robots creation flow already uses:

- **Text/narrative content** (Dream titles, descriptions, character
  backstories, reward flavor text): `server/api/chats/*` — e.g.
  `chats/index.post.ts`, or a provider stream route
  (`chats/anthropic/stream.post.ts` / `chats/openai/stream.post.ts`) driving
  a prompt that fills a Dream/Character/Reward's text fields.
- **Art** (per-item `imagePath`/`cardPath`/`heroPath`/`artPrompt`):
  `server/api/art/generate.post.ts` (or `enqueue.post.ts` for the async
  queue path — `server/api/art/queue/*`), then
  `server/api/art/save-generated.post.ts` to attach the result to the
  Dream/Character/Facet/Reward row via its `artImageId`.
- **Persisting the generated record**: `server/api/dreams/index.post.ts`
  (Dreams), and the equivalent create routes for `Character`/`Reward`/
  `Facet` (Facet has no dedicated `server/api/facets/` directory found in
  this audit — if one doesn't exist, creating Facet rows for a pack's genre
  entries is itself a small, additive kind_robots task, not a packmaker
  concern).

Per BOUNDARY.md, kind_robots' generation endpoints, auth, and database are
**consumed as external services** — packmaker's admin/generator UI calls
these routes exactly as any other kind_robots feature would, and never
adds new generation logic, cost accounting, or model selection of its own.
If a pack ever needs something the existing pipelines can't do (a new
generation mode, a new model field), that becomes a kind_robots pitch, not
a direct edit.

## 3. Admin view vs. user view

**Admin view** (Silas only, per §4's ownership model): load a pack manifest
(t-002's schema), run/re-run generation per item through the pipelines in
§2, review the results inline, and mark the pack `ready-to-release`. This
is the "generator front end" from t-004/m3 — the whole point is making the
*next* pack (after Uncanny Valor/Arcane Whimsy) cheap to produce, so this
view should be manifest-driven rather than hardcoded per pack.

**User view**: already scaffolded (t-005, kind_robots PR #204) —
`components/conductor/packmaker-page.vue` wraps the reusable
`ProjectFrontPage` scaffold (`components/conductor/project-front-page.vue`)
with a `slug: "packmaker"` + static `fallback: ProjectFrontConfig`, rendered
at `/packs` via the Nuxt Content catch-all
(`content/packs.md` → `pages/[...slug].vue`). Today it's pure placeholder
marketing copy — no real pack data. `ProjectFrontPage` already merges a
live `Project` DB record (title/flavorText/description/icon/status) over
the static fallback and exposes an empty `#interactive` slot plus an
optional `ProjectGalleryStrip` keyed by an `ArtCollection` label. The real
pack browse/preview/owned-unlocks UI (t-004/m3, once the admin generator
exists) should land inside that `#interactive` slot rather than replacing
the scaffold, following the same slug+fallback pattern any other project
front page uses. The `ProjectGalleryStrip` hook is also a natural fit for
"here's a preview gallery of this pack's art" using each pack's cover
`ArtCollection`.

## 4. Ownership and privacy — interim state, pending kind-robots t-008

**kind-robots t-008 (private-but-shared content + per-user project
sharing, `projects/kind-robots/SHARING-SPEC.md`) has not been written yet**
(still `status: ready` as of this brief) — so there is no grant/ACL model
to build against today. This brief does not invent one. Concretely, the
only visibility primitives that exist right now on every candidate item
model (`Dream`, `Facet`, `Character`) are the same triad:
`isPublic: Boolean @default(true)`, `isMature: Boolean @default(false)`,
`isActive: Boolean @default(true)`. `ArtCollection` carries the same
triad. There is no `releasedAt`/`visibility` enum/entitlement field
anywhere in the schema, and the only "unlock" pattern that exists at all is
`LifeAchievementUnlock` — a Da Vinci-specific per-user achievement log, not
a general ownership grant.

**Interim rule until t-008 lands:** a pack's items are created with
`isPublic: false` (drafts, tied to Silas as `userId`) while the pack is in
progress. "Releasing" a pack today can only mean flipping `isPublic: true`
on its items — an all-or-nothing switch, not a per-purchaser grant. That is
good enough for the free/public launch path but **not** sufficient for the
DLC-unlock use case (§5), where only *purchasers* should see the content
while everyone else shouldn't. The DLC path is explicitly blocked on t-008
producing a real grant model — packmaker should not build a parallel
permission system to route around that gap (per the 2026-07-05 TALKBACK
review of this project). Until t-008 lands, DLC packs stay `isPublic: false`
end-to-end (visible only via direct admin/Prisma access), which is
conservative but safe.

## 5. Mapping to digital-storefront purchases (t-017)

digital-storefront's SPEC.md (t-009) already designed the general-purpose
piece packmaker needs: an `Entitlement { userId, productId, orderItemId,
grantedAt, revokedAt }` model, created by the Stripe webhook on
`checkout.session.completed`, that answers "does this user own this
digital good" for *any* `Product` — deliberately including a `DLC` product
type in that same spec, described as "the same shape for both current v1
digital goods (Mermaids of Venice PDF) and future ones (Uncanny Valor /
Arcane Whimsy DLC packs from packmaker) — one model, no product-type-
specific entitlement tables."

Packmaker should build against that plan rather than designing its own
entitlement mechanism:

- A DLC pack becomes one `Product` row (`type: DLC`, `metadata: { packSlug:
  "uncanny-valor" }`).
- A successful purchase creates an `Entitlement` row exactly as any other
  digital good would.
- The pack's actual content-access check (does this user's client get to
  see/use the pack's Dreams/Characters/Rewards) is a **feature/route gate**
  reading `GET /api/store/entitlements` (per digital-storefront SPEC.md
  §5's DLC description), not a download — packmaker's front end checks the
  caller's entitlement slugs before rendering unlocked pack content.
- This still needs kind-robots t-008 for the underlying per-item visibility
  answer (§4) — the `Entitlement` row proves *purchase*, but making the
  actual `Dream`/`Character` rows selectively visible to only that
  purchaser (rather than all-or-nothing `isPublic`) is exactly the grant
  model t-008 is supposed to define. digital-storefront/t-017 already
  tracks this as a note-level cross-project dependency; this brief doesn't
  duplicate that tracking, just confirms the entitlement half of the design
  is already solved and packmaker shouldn't reinvent it.

## 7. Open questions for Silas (soft needs-human, non-blocking)

- **Character item type**: should pack "character" entries default to the
  lightweight `Dream` (`dreamType: CHARACTER`) shape, or the richer
  standalone `Character` model (stats, class, species)? This brief
  recommends `Character` for packs meant to power builder/game content
  (Uncanny Valor/Arcane Whimsy sound like they want real stat blocks), but
  Silas may want lore-only Dream entries for some packs and full
  `Character` rows for others — the manifest schema (t-002) should
  probably let a pack declare which shape it wants per item, not hardcode
  one.
- **Pack container model**: is a YAML manifest in `projects/packmaker/packs/`
  sufficient indefinitely, or does repeatable, admin-driven pack creation
  (t-004) eventually need a real `Pack`/`PackItem` Prisma model in
  kind_robots (so the admin UI can list/edit packs without a conductor
  round-trip)? Recommend deferring this decision to t-004, once there's a
  concrete admin-UI need driving it — raising it now as a pitch would be
  premature per the "brief stays a brief" note from this project's own
  TALKBACK history.
