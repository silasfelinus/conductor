## 1. What's already true (from STORE-AUDIT.md)

- Checkout Sessions and Subscription Sessions both work today up to the
  Stripe redirect. Nothing downstream of a successful payment exists.
- The only durable commerce state is `User.stripeCustomerId`.
- No `Order`/`Purchase`/`Product`/`Subscription` Prisma models exist.
- The Stripe checkout route prices against a hardcoded seed array
  (`stores/seeds/cartItems.ts`), imported straight into the server route.
- Neither Stripe route has an auth guard tying `userId` to the caller.

This brief's job is to close those gaps for the v1 catalog: Mermaids of
Venice PDF, KR-logo POD item, monthly subscription, mana top-ups, Against
Malaria giving page, DLC unlocks — without touching the four hard rules
above.

## 2. Stripe architecture: Checkout Sessions + webhook → fulfillment

**Keep Checkout Sessions** (already in use) rather than Payment Intents —
Stripe hosts the payment page, no PCI surface in kind_robots, and both the
one-time (`checkout.post.ts`) and subscription (`subscribe.post.ts`) flows
already use this pattern correctly.

**Add the missing half: a webhook handler.**

- New route: `server/api/stripe/webhook.post.ts`.
- Verify every event with `stripe.webhooks.constructEvent(rawBody, signature,
  STRIPE_WEBHOOK_SECRET)` — this requires reading the **raw** request body
  before any JSON body-parsing middleware touches it (Nuxt/Nitro: use
  `readRawBody(event)`, not `readBody(event)`). This is the one route in the
  app that must not go through the normal JSON-parse path.
- New env var: `STRIPE_WEBHOOK_SECRET` (test-mode value from `stripe
  listen --forward-to` during dev; production value only after Silas
  provisions a live webhook endpoint — never before).
- Events to handle for v1:
  - `checkout.session.completed` (mode `payment`) → look up the session's
    `client_reference_id` (set this to the internal `userId` at session
    creation, in addition to the existing `metadata`) and `line_items` →
    create an `Order` + `OrderItem` row (see §3) → fan out to
    fulfillment per item type (§4).
  - `checkout.session.completed` (mode `subscription`) → flip
    `User.isMember = true`, store the Stripe subscription id.
  - `customer.subscription.deleted` / `customer.subscription.updated`
    (status `canceled`/`unpaid`) → flip `User.isMember = false`.
  - `invoice.paid` (subscription renewal) → optional mana grant per
    `notes_from_silas`'s "monthly supporter subscription" language, using
    the existing `ManaReason.SUBSCRIPTION_GRANT` enum value that already
    exists in schema but has no writer today.
- Idempotency: Stripe retries webhook delivery on non-2xx responses and can
  redeliver the same event id. Store processed `stripe_event_id`s (a small
  `WebhookEvent { id, type, processedAt }` table, or reuse `Order.stripeSessionId`
  as a uniqueness constraint) and short-circuit a duplicate delivery instead
  of double-fulfilling.
- Auth: Stripe's own signature verification IS the auth for this route —
  do not add `validateApiKey`, since the caller is Stripe, not a logged-in
  user.

**Close the existing auth gap** (STORE-AUDIT §7) while touching these routes:
`checkout.post.ts` and `subscribe.post.ts` should verify the caller's session
matches the `userId` in the request body the same way `mana/[id].get.ts`
and `socials/[id]/publish.post.ts` already do (`validateApiKey` + self-or-ADMIN
check), rather than trusting an unauthenticated `userId` field. This matters
more once the webhook starts crediting mana/membership off that same id.

## 3. Catalog and order data model (new Prisma models)

Move pricing out of the imported seed file and into the database so the
catalog can grow past six hardcoded rows without a code deploy:

```prisma
model Product {
  id            String   @id @default(cuid())
  slug          String   @unique          // "mermaids-pdf", "kr-logo-mug", "mana-100", ...
  type          ProductType               // enum: DIGITAL_PDF | POD | SUBSCRIPTION | MANA_TOPUP | DLC | DONATION
  title         String
  priceCents    Int
  currency      String   @default("usd")
  active        Boolean  @default(true)
  metadata      Json?                     // POD variant id, DLC pack slug, mana amount, etc.
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  orderItems    OrderItem[]
}

model Order {
  id                String      @id @default(cuid())
  userId            Int
  user              User        @relation(fields: [userId], references: [id])
  stripeSessionId   String      @unique
  stripeCustomerId  String?
  status            OrderStatus @default(PENDING) // PENDING | PAID | FAILED | REFUNDED
  totalCents        Int
  createdAt         DateTime    @default(now())
  items             OrderItem[]
}

model OrderItem {
  id          String   @id @default(cuid())
  orderId     String
  order       Order    @relation(fields: [orderId], references: [id])
  productId   String
  product     Product  @relation(fields: [productId], references: [id])
  quantity    Int      @default(1)
  priceCents  Int              // snapshot at purchase time, independent of later Product price changes
}

model Entitlement {
  id          String   @id @default(cuid())
  userId      Int
  user        User     @relation(fields: [userId], references: [id])
  productId   String
  product     Product  @relation(fields: [productId], references: [id])
  orderItemId String   @unique
  grantedAt   DateTime @default(now())
  revokedAt   DateTime?
}
```

`Product` replaces `stores/seeds/cartItems.ts` as the trusted price source
for `checkout.post.ts` — the route should query `prisma.product.findMany({
where: { slug: { in: requestedSlugs }, active: true } })` instead of
importing the client-side seed array, closing the client/UI-catalog
mismatch STORE-AUDIT flagged (§3 of that doc). `stores/seeds/cartItems.ts`
becomes a one-time seed script input (`prisma db seed`), not a runtime
import into a server route.

`Entitlement` is the answer to "does this user own this digital good" —
described further in §4.

## 4. Entitlement model for digital goods (PDF, DLC unlocks)

A purchase of a `DIGITAL_PDF` or `DLC` product creates one `Entitlement` row
(via the webhook, on `checkout.session.completed`) linking `userId` →
`productId`. Access checks (download endpoint, DLC unlock gate) query
`Entitlement` directly — no need to walk back through `Order`/`OrderItem`
for a simple yes/no check. `revokedAt` covers refunds (set by a future admin
action or a `charge.refunded` webhook event, out of scope for v1 but the
column exists so refund-handling doesn't need a migration later).

This is deliberately the same shape for both current v1 digital goods
(Mermaids of Venice PDF) and future ones (Uncanny Valor / Arcane Whimsy DLC
packs from packmaker) — one model, no product-type-specific entitlement
tables.

## 5. Secure delivery of paid files

**Hard constraint from `notes_from_silas`: the novel PDF must never sit in
`public/` or any publicly reachable repo path.** Concretely:

- Store the actual PDF file outside the Nuxt `public/` directory and outside
  the git repo entirely — object storage (the same pattern used elsewhere in
  kind_robots for generated art assets, if one exists — confirm during
  implementation) or a private local path the server process can read but
  Nitro's static file server never serves.
- New route: `server/api/store/download/[productId].get.ts`.
  - `validateApiKey(event)` to identify the caller.
  - Query `Entitlement` for `{ userId: caller.id, productId, revokedAt: null }`
    — 403 if no row.
  - Stream the file from private storage, or (if using object storage that
    supports it) generate a short-lived signed URL (5–15 minute expiry) and
    redirect — avoids proxying large file bytes through the Nitro process.
  - Do **not** put the file path or a permanent URL in any client-visible
    state (Pinia store, `Entitlement.metadata`, etc.) — always re-check
    entitlement per download request.
- DLC "unlocks" (website content, not a downloadable file) follow the same
  `Entitlement` check but gate a feature/route instead of streaming bytes —
  e.g. a Nuxt middleware or component-level check against
  `GET /api/store/entitlements` (returns the caller's own entitlement slugs)
  rather than a download route.

## 6. Mana crediting

- One-time top-ups: a `Product` row with `type: MANA_TOPUP` and
  `metadata: { manaAmount: 100 }`. On `checkout.session.completed`, the
  webhook handler writes a `ManaTransaction` with `reason: PURCHASE`,
  `amount: metadata.manaAmount`, and increments `User.mana` — this is the
  first writer of `ManaReason.PURCHASE`, which exists in the schema today
  with no code path producing it (STORE-AUDIT §4).
- Subscription grants: on `invoice.paid` for an active subscription, write a
  `ManaTransaction` with `reason: SUBSCRIPTION_GRANT` (same "enum exists,
  no writer" gap). Amount is a `Product`/subscription-tier-level constant,
  not user-configurable.
- `credit-purchase.vue` (currently a full mock — STORE-AUDIT §2) becomes the
  real UI for `MANA_TOPUP` products once this lands: replace its hardcoded
  `creditOptions` array and fake `setTimeout` purchase with `Product` rows
  fetched from a new `GET /api/store/products?type=MANA_TOPUP` route and a
  real `cartStore.checkout()` call, matching the pattern `shopping-cart.vue`
  already uses correctly.

## 7. Subscription handling

- `subscription-manager.vue`'s `startSubscription()` path is already correct
  (STORE-AUDIT §2) — no change needed there.
- `User.isMember` gets its first writer via the webhook (§2): true on
  `checkout.session.completed` (subscription mode) and on `invoice.paid`
  renewal; false on `customer.subscription.deleted` or a `status: canceled`/
  `unpaid` update.
- **Cancellation** (`cartStore.cancelSubscription()` is currently a stub that
  always returns `success: false` — STORE-AUDIT §2/§3): implement a new
  route `server/api/stripe/cancel-subscription.post.ts` that calls
  `stripe.subscriptions.update(subId, { cancel_at_period_end: true })` (soft
  cancel — access continues until the paid period ends, matching normal SaaS
  UX) rather than `stripe.subscriptions.cancel()` (immediate). The
  `customer.subscription.updated` webhook event then flips `isMember` when
  the period actually ends, keeping a single source of truth for the flag
  instead of the client route setting it directly.
- Store the live Stripe subscription id on `User` (new column,
  `stripeSubscriptionId String?`) so the cancel route knows which
  subscription to target without a Stripe API list-call.

## 8. Admin vs. user views

- **User view**: existing `mana-wallet.vue` (real, keep), `subscription-manager.vue`
  (real start path; add real cancel per §7), a new "My purchases" panel
  reading `GET /api/store/orders?userId=me` (paid orders + entitlements —
  useful for "redownload my PDF" without re-purchasing), and the
  entitlement-gated DLC surfaces per §4.
- **Admin view**: a `Role: ADMIN`-gated page (mirroring the existing
  admin-check pattern in `socials/[id]/publish.post.ts` and `mana/[id].get.ts`)
  listing recent `Order` rows, their status, and a manual "mark refunded"
  action that sets `Order.status = REFUNDED` and `Entitlement.revokedAt =
  now()` — a stopgap until a `charge.refunded` webhook handler exists.
  Product management (add/edit/deactivate a `Product` row) can start as
  direct Prisma Studio/DB access for v1; a dedicated admin CRUD UI is a
  reasonable m4/m5 follow-up, not a v1 blocker.

## 9. What each v1 catalog item needs, mapped to this spec

| Item | Needs from this spec |
|---|---|
| Mermaids of Venice PDF | `Product` (DIGITAL_PDF) + webhook → `Entitlement` (§3–4) + secure download route (§5) |
| KR-logo POD item | `Product` (POD) + webhook fulfillment step that calls the POD vendor (vendor choice is t-015, separate task; out of scope here) |
| Monthly subscription | Webhook-driven `isMember` flip + real cancel route (§7) |
| Mana top-ups | `Product` (MANA_TOPUP) + webhook `ManaTransaction` write (§6) + `credit-purchase.vue` rewire |
| Against Malaria giving page | Content/layout only (t-014); the existing `donation` seed item becomes a `Product` (DONATION) if kept as a convenience add-on, per roadmap direction that the page must lead with the direct `againstmalaria.com/amibot` link |
| DLC unlocks (packmaker output) | `Product` (DLC) + `Entitlement` gate (§4); blocked on packmaker producing content first, independent of this spec |

**Suggested build order** (each independently landable): (1) `Product`/`Order`/
`OrderItem`/`Entitlement` migration + seed script replacing the imported
array, (2) webhook handler with `checkout.session.completed` (payment mode)
only, wired to the PDF product, (3) secure download route, (4) subscription
webhook events + real cancel route, (5) mana top-up wiring, (6) admin order
list. This lets the Mermaids of Venice PDF go live (in test mode) after step
3 without waiting on subscriptions or mana.
