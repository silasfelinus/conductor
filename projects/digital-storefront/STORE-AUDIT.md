# STORE-AUDIT.md — kind_robots giftshop/Stripe surface

Generated by: digital-storefront/t-008
Date: 2026-07-15
Scope: kind_robots repo — `server/api/stripe/`, `components/giftshop/`,

---

## TL;DR

Stripe checkout and subscription creation work end to end **up to the point of
redirecting the user to Stripe's hosted page**. Nothing downstream of a
successful payment exists: there is no webhook handler, no order/purchase
record, no mana credit on purchase, and no `isMember` flip on subscribe. The
product catalog priced into Stripe is a demo seed file, not a real catalog.
Roughly half of the giftshop UI components are wired to real state (cart,
mana, social); the other half are visual stubs (`alert()`/`console.log()`
placeholders) that look finished but do nothing. Auth is inconsistent: the
mana and social routes check the caller is who they claim to be, the two
Stripe routes do not.

## 1. Stripe server routes

### `server/api/stripe/checkout.post.ts`

- **Stripe client**: lazy singleton (`getStripeClient()`), instantiated
  inside the request handler — **the server does not crash on boot** if
  `STRIPE_SECRET_KEY` is unset (this was flagged as a boot-crash risk in the
  original task note; it is not one — good). Missing key instead produces a
  per-request 500 with `'Stripe secret key is not configured'`.
- **Flow**: `{ userId, cart }` in → look up `User` (404 if missing) → get/create
  Stripe customer, persisting `stripeCustomerId` back onto `User` → price the
  cart against **`stores/seeds/cartItems.ts`**, imported directly into the
  server route as `trustedItems` (with an inline `// TODO: move cartItems to
  server location if needed — this is for demo` comment) → create a
  `mode: 'payment'` Checkout Session → return `{ success, url }`.
- **The seed file is the live pricing source today**, not just UI demo data —
  a real purchase would be priced off `stores/seeds/cartItems.ts`'s 7 items
  (print $12.99, shirt $24.99, sticker $4.99, mug $16.49, donation $1,
  100 tokens $5, signed book $20).
- **No auth check** that `userId` in the request body is the calling user —
  only that it maps to an existing `User` row.

### `server/api/stripe/subscribe.post.ts`

- Same lazy-client, same no-auth pattern.
- `STRIPE_PRICE_ID` is read with a non-null assertion (`!`) and no presence
  check — if unset, Stripe's API rejects the session server-side rather than
  failing locally with a clear error.
- Redirects to `/members/success` / `/members/cancel` (checkout.post.ts uses
  `/shop/success` / `/shop/cancel` instead) — two different post-purchase
  destinations; neither was confirmed to exist as a page in this pass.

### Webhooks: none exist

No `server/api/stripe/webhook*.ts`, no call to `stripe.webhooks.constructEvent`
anywhere in the repo, and no `STRIPE_WEBHOOK_SECRET` env var defined anywhere
(only `STRIPE_SECRET_KEY` is, in `docker-compose.yml`).

**Consequence**: nothing in the codebase ever learns that a Stripe payment
actually succeeded. `stripeCustomerId` gets written at *session-creation*
time (before payment); nothing writes a `ManaTransaction`, flips
`User.isMember`, or records a completed sale afterward. Building a webhook
handler for `checkout.session.completed` / subscription events is the single
biggest missing piece between "Stripe checkout page opens" and "a purchase
does anything."

### Auth gap

Compare the Stripe routes to `server/api/mana/[id].get.ts` and
`server/api/socials/[id]/publish.post.ts`, both of which call
`validateApiKey(event)` and check `user.id !== id` before acting. The Stripe
routes have no equivalent — any caller who can reach the API and knows (or
guesses) another user's numeric ID can trigger a Stripe customer
creation/checkout session attributed to that user. Low severity while nothing
downstream trusts the session (no webhook consumes it), but must be fixed
before webhooks start crediting mana or granting membership off `userId`.

## 3. Catalog and cart store

- **`stores/seeds/cartItems.ts`** (7 items, table above) is imported by the
  *server* checkout route as the trusted price list — it is the real catalog
  today, not fallback data, despite living under `seeds/` and being commented
  as "for demo." None of the giftshop UI components actually render this
  list — `giftshop-interact.vue` uses its own separate, smaller hardcoded
  array instead. **There is a live mismatch between what the UI shows and
  what Stripe would actually charge for.**
- **`stores/cartStore.ts`** is Pinia + `localStorage` only (key `cartItems`,
  synced via a `deep: true` watcher) — no server-side cart persistence exists.
  `checkout(userId)` builds `{ id: item.type, quantity }` from cart contents
  (using `item.type`, not `item.id`, as the id sent to the server) and relies
  on `type` strings matching the seed catalog's `id` values — an untyped,
  implicit contract across the client/server boundary worth hardening before
  the catalog grows.
- `subscribe()` is real (POST + redirect); `cancelSubscription()` is a stub
  (see table above).

## 4. Prisma schema — what's durable

**No `Order`, `Purchase`, `Cart`/`CartItem`, `Subscription`, or `Product`
model exists anywhere in the schema.** Commerce state lives entirely on
`User`:

| Field | Written by | Notes |
|---|---|---|
| `User.stripeCustomerId` | `checkout.post.ts`, `subscribe.post.ts` | Set at session-creation time (before payment). |
| `User.mana` / `lastManaRefill` / `manaCap` | `server/utils/refill.ts` and mana routes | Unrelated to Stripe purchases today. |
| `User.isMember` | **nothing** | No writer found anywhere. `ManaReason` enum includes `PURCHASE` and `SUBSCRIPTION_GRANT` values, implying purchase-driven mana grants and membership flips were planned, but no code path inserts either. |
| `ManaTransaction` | mana routes only | Never written to from a Stripe flow. |

**Net**: a completed Stripe payment today leaves no local trace beyond a
pre-payment `stripeCustomerId`. Whatever Stripe's own dashboard records is
the only source of truth for "did someone actually pay."

## 5. Print-on-demand (POD)

**0% wired.** No Printful/Printify/Prodigi/Gooten integration anywhere in the
repo (confirmed by grep across the tree). What exists:
- `print-swag.vue` — UI scaffold only, stub `addToCart()` (§2).
- Marketing copy in `content/channels/sanctuary/giftshop.md` and
  `components/pages/about-page.vue` mentioning POD as a future plan, plus a
  reference to an **external, unintegrated** Redbubble storefront run by
  "sister organization Cafe Purr" — not part of this codebase.
- No Prisma fields for print type, order status, or vendor order IDs.

This matches `digital-storefront/roadmap.yaml`'s hard rule: no POD account
creation without Silas (needs-human, unchanged by this audit).

## 6. Social publishing (`social-publisher.vue`)

Genuinely the most complete piece of the giftshop-adjacent surface:
- Real CRUD via `useSocialStore()` → `server/api/socials/*` → Prisma
  `SocialPost`/`SocialTarget`.
- `publish.post.ts` **does** call `validateApiKey(event)` and enforce
  owner-or-ADMIN — the one route in this audit with a proper auth guard.
- Per-platform dispatch: **Discord** is a real webhook POST (env
  `DISCORD_WEBHOOK_URL`); **Mastodon** and **Bluesky** are explicit stubs
  that throw `NotWiredError` and resolve to `SKIPPED` (by design, not a bug
  — comments document the intended API shape for each); **Reddit / Facebook
  / Instagram** are deliberately manual (copy-paste + "Mark Copied" flow),
  never automatable by design.
- Scheduling field exists (`scheduledAt`) but has an explicit TODO noting it
  needs a cron/queue worker that doesn't exist yet; the UI intentionally
  omits scheduling controls until that lands.
- Per-platform formatting/truncation logic (`utils/social/formatSocialPost.ts`)
  is fully implemented, not placeholder.

## What each v1 catalog item still needs

Per `roadmap.yaml`'s fixed v1 catalog (Mermaids of Venice PDF, KR-logo POD
item, monthly subscription, mana top-ups, Against Malaria giving page, DLC
unlocks):

1. **Mermaids of Venice PDF / any digital-download item** — checkout route
   exists and prices correctly against the seed catalog once a real `book`-type
   entry is confirmed; still needs (a) a webhook to know payment succeeded,
   (b) a fulfillment step that actually delivers the file/access, (c) a real
   product card in `giftshop-interact.vue` (currently shows unrelated demo
   items).
2. **KR-logo POD item** — needs a POD vendor integration from scratch (§5);
   `print-swag.vue`'s UI shell exists but is fully disconnected.
3. **Monthly supporter subscription** — checkout-initiation works
   (`subscription-manager.vue` → `/api/stripe/subscribe`); needs a webhook to
   flip `User.isMember` on success and a real cancellation path (`cancelSub()`
   is currently a stub).
4. **One-time mana top-ups** — no code path connects a Stripe purchase to a
   `ManaTransaction` write; `credit-purchase.vue` is fully mocked and doesn't
   even use the real seed catalog's `tokens` item.
5. **Against Malaria giving page** — content/layout task (t-014, separate);
   the seed catalog already has a `donation` item priced at $1 that could
   back an optional convenience add-on, per the roadmap's direction that the
   page should lead with the direct `againstmalaria.com/amibot` link.
6. **DLC packs (packmaker output)** — no catalog entries or delivery
   mechanism exist yet; blocked on packmaker producing content first.

**Cross-cutting prerequisite for all six**: a Stripe webhook handler
(`checkout.session.completed`, subscription lifecycle events) is the one
piece of infrastructure every item above needs and none of them have. This
is the highest-leverage next `software` task for this project.

## Secondary findings (not blocking, worth a kaizen task)

- Two independent, out-of-sync checkout UIs (`cart-interact.vue` stub vs.
  `shopping-cart.vue` real) — one should be retired.
- `giftshop-interact.vue`'s showcase items and `stores/seeds/cartItems.ts`
  are two different catalogs; the UI a shopper sees does not match what
  Stripe would actually charge.
- No auth guard on the two Stripe routes (§1, §7) — low severity today since
  nothing downstream trusts the session, but must be closed before a webhook
  starts crediting mana/membership off `userId`.
- Stale header-comment paths in six giftshop components (cosmetic).
