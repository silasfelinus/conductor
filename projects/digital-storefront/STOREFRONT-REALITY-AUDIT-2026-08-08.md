## Cross-cutting: Stripe webhook & general cart checkout — **BUILT-AND-VISIBLE, with one nuance**

- `webhook.post.ts` handles `checkout.session.completed` (routed by
  metadata/mode into mana top-up / subscription / single-product / general-cart
  handlers) and `customer.subscription.updated`/`.deleted`.
- Correct auth model: the webhook has no `requireApiUser` guard — it verifies
  `stripe.webhooks.constructEvent()` with `STRIPE_WEBHOOK_SECRET` instead, which
  is the right pattern for a webhook. Every user-initiated Stripe/store route
  (`checkout.post.ts`, `subscribe.post.ts`, `topup.post.ts`,
  `cancel-subscription.post.ts`, `product-checkout.post.ts`,
  `pod-checkout.post.ts`, `checkout-status.get.ts`) now calls `requireApiUser`.
  This closes the "no auth guards" gap from 2026-07-15.
- Idempotency: `Order.stripeSessionId` is `@unique`; every fulfillment path
  checks for an existing `Order`/`ManaTransaction` before writing. (Design
  confirmed by inspection, not runtime-verified against a real Stripe retry.)
- **Gap: two parallel pricing sources coexist.** The general cart
  (`checkout.post.ts`) still prices strictly from `stores/seeds/cartItems.ts` (a
  hardcoded TS array; `parseCart` rejects any `id` not in it), while
  `product-checkout.post.ts`/`pod-checkout.post.ts` price off the real `Product`
  DB table.
- Real `artImageId` threading and POD eligibility: `checkout.post.ts:129-212`
  requires/validates `artImageId` for `needsArt` types and re-checks
  `checkPrintEligibility()` server-side before creating the session. The webhook
  re-checks eligibility **again at fulfillment time** via the shared helper
  `createPrintJobIfEligible()` (`webhook.post.ts:135-188`), used by both the
  single-product POD branch and the general-cart POD branch — this confirms
  both the "shared helper" and "re-check eligibility at webhook time" roadmap
  claims by reading the actual logic, not just comments.
  `checkPrintEligibility()` reads `Resource.commercialSafe`, confirming t-029.

- **Dedicated single-item POD flow: BUILT-BUT-UNREACHABLE.**
  `server/api/store/pod-checkout.post.ts` is fully real (auth, eligibility,
  Product-table-backed), but its only UI, `print-swag.vue`, was moved to
  `components/abandonware/giftshop/print-swag.vue` — `nuxt.config.ts:260`
  excludes `abandonware/**/*.vue` from auto-import, and
  `docs/wonderlab-component-retirement-policy.md` confirms this is the formal
  "retired" convention. No live `<print-swag>`/`PrintSwag` usage exists outside
  that directory. The route works; nothing in the running app points at it.
- **Vendor fulfillment (t-040): confirmed unstarted, precisely.**
  `PrintJobStatus`'s own schema comment: *"PENDING is the only status reachable
  until the Printful vendor integration itself is built (needs-human — no

  `podCatalog.ts` variant IDs remain placeholder strings. PrintJobs are created

## Real gaps remaining (feeds t-038 / t-039 / t-040 / t-041 directly)

1. Two parallel pricing sources: `checkout.post.ts` prices off
   `stores/seeds/cartItems.ts` (hardcoded array); `product-checkout.post.ts` /
   `pod-checkout.post.ts` price off the real `Product` table. Needs a decision:
   retire the seed array in favor of `Product` rows, or confirm the split is
   intentional.
2. No KR-logo `Product` exists — needs a seeded catalog entry with a fixed
   `artImageId` for the KR logo image (or a dedicated non-art-dependent SKU).
3. DLC has no live catalog and no creation path — needs an admin
   route/script to turn a Packmaker `Pack` into a `Product` with
   `metadata.packId`, and the content-consumption side
   (`contentAccess.ts`'s packId check) still needs wiring into the actual
   Dream/Facet/Character/Reward content routes.
4. t-040's scope confirmed precisely: no real POD vendor (Printful)
   integration exists anywhere — `printfulOrderId` never set,
   `podCatalog.ts` variant IDs are placeholders, `PrintJobStatus` never
   advances past PENDING/FAILED.
5. `pod-checkout.post.ts`'s dedicated single-item POD flow is orphaned —
   either restore a live entry point (e.g. an art-detail/gallery "Print this"
   action) or formally decide the general-cart featured-art path is the sole
   POD UI and drop the dedicated route.
6. `giftshop-interact.vue`'s hardcoded demo showcase items ("Butterfly
   Print"/"Jellybean Token Pack", guessed `artImageId`s) should be replaced or
   removed now that the real `storefrontFeatured`-backed section exists
   directly above them.
7. `giftshop-manager.vue`'s tab-switch doesn't explicitly handle
   `activeTab === 'mermaids'` in-place — currently masked by always routing
   away first; worth a defensive fix.
8. Not verifiable from a code-only audit: whether the webhook actually
   receives and correctly processes live Stripe events in the deployed
   environment, whether `STRIPE_WEBHOOK_SECRET`/`STRIPE_SECRET_KEY`/
   `STRIPE_PRICE_ID` are correctly configured in production, and whether
   idempotency holds under a real Stripe retry. All of the above is "correct
   by inspection," not "observed working" — this is exactly t-039's scope.
